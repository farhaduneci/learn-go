Shared memory: sync, atomics & the memory model

Most production Go state is protected by mutexes, not channels. This lesson covers the sync toolbox, lock-free atomics, and the memory model's happens-before rule that decides whether code is correct at all.

On this page
Primary source
The Go Memory Model (read the introduction and "Advice" first), Data Race Detector, and the sync package docs.

What a data race is

A data race is two goroutines accessing the same memory at the same time, at least one of them writing, with no synchronisation between them. In Go a race is undefined behaviour: torn reads, lost updates, or corrupted maps and slices. Python's GIL hid most of these (counter += 1 was still unsafe, just rarely wrong). Go runs goroutines truly in parallel, so they show up under load.

count++ // read, add, write: three steps; two goroutines can interleave and lose updates

Always run tests with -race. The detector instruments memory accesses and reports both conflicting stacks. It finds only races that actually happen during the run, so tests must exercise the concurrency. It adds roughly 5–10× CPU and memory overhead: fine in CI, usually too much for production.

sync.Mutex and RWMutex

type Positions struct {
    mu  sync.Mutex        // guards qty; convention: the mutex sits above the fields it guards
    qty map[string]int64
}

func (p *Positions) Apply(sym string, d int64) {
    p.mu.Lock()
    defer p.mu.Unlock()
    p.qty[sym] += d
}
  • The zero value is an unlocked mutex. Never copy a struct holding one: use pointer receivers. go vet (copylocks) catches copies.
  • Keep critical sections short, and never do I/O or send on a channel while holding a lock. That's how latency spikes and deadlocks start.
  • defer Unlock() is cheap (open-coded defers since Go 1.14). Hand-unlocking pays off only in the hottest paths.
  • sync.RWMutex lets many readers in parallel (RLock) and one writer at a time. It only helps when reads greatly outnumber writes and critical sections aren't tiny. Otherwise its extra bookkeeping makes it slower than a plain Mutex. Measure.
  • Go mutexes are not reentrant. Locking twice in the same goroutine deadlocks.

sync/atomic

For single counters, flags or pointers, atomics avoid locks entirely:

var n atomic.Int64
n.Add(1); n.Load(); n.Store(0); n.CompareAndSwap(old, new)

var cfg atomic.Pointer[Config] // lock-free config hot-swap: readers Load, a writer Stores a new pointer

Use the typed atomics (atomic.Int64, atomic.Bool, atomic.Pointer[T], Go 1.19+). They can't be accidentally read non-atomically. Atomics are fast (a few ns, uncontended) but only protect one word. Keeping two fields consistent with each other needs a mutex.

False sharing: two atomics updated by different cores that sit in the same 64-byte cache line slow each other down. Padding (_ [56]byte) separates hot counters. That's a real low-latency technique, used only after a profile shows the problem.

Once, OnceValue, Pool, Cond, sync.Map

  • sync.Once, sync.OnceFunc, sync.OnceValue(s): lazy, thread-safe, exactly-once initialisation.
  • sync.Pool: a cache of reusable objects that cuts allocations on hot paths (lesson 18). Pooled objects can disappear at any GC.
  • sync.Map: specialised for keys written once and read many times, or disjoint key sets per goroutine. For everything else a map plus Mutex is simpler and often faster.
  • sync.Cond: rarely the best tool. Channels usually express the same thing more clearly.

The memory model in one rule

Without synchronisation, there's no guarantee one goroutine ever sees another's write, or sees writes in the order they were made. Guarantees come from happens-before edges:

  • A send on a channel happens before the matching receive completes.
  • Closing a channel happens before a receive that returns because it's closed.
  • Unlock happens before the next Lock of the same mutex.
  • wg.Done() happens before the wg.Wait() it unblocks, and once.Do(f) completing happens before any Do returns.
  • Atomic operations are sequentially consistent.

That's why exercise 08's per-index writes are safe to read after wg.Wait(), and why a "just a boolean flag" loop like for !done {} may never terminate. The compiler is allowed to hoist the read out of the loop.
